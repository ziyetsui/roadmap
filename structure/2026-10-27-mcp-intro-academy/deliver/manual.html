        步骤 1 先弄清 MCP 替你省掉了什么

        课程第一课和第二课只讲概念，但后面每一步都在补这张图里的一段。先把“一次工具调用要经过谁”画清楚，后面写代码时就知道自己在补哪一段。

        目标：能用课程的 GitHub 例子，说出没有 MCP 时要自己写什么、有了 MCP 之后谁来写。

        1. 读 L1。课程的例子是：做一个能回答用户 GitHub 问题（L2 用的是“我有哪些仓库”）的聊天应用，没有 MCP 就得自己为 GitHub 的大量功能写工具定义和调用代码，还要长期维护；有了 MCP，这些交给一个专门的 GitHub MCP 服务器，你的应用只负责连上它[O1]。
        2. 记住 L1 结尾三个问答的结论：MCP 服务器谁都能写，常见的是服务商官方出；和直接调 API 的区别是工具定义已经写好；MCP 不等于 tool use，tool use 讲的是 Claude 怎么调用工具，MCP 讲的是工具由谁来实现[O1]。
        3. 读 L2，认两对消息：ListToolsRequest/Result（问服务器有哪些工具）和 CallToolRequest/Result（让服务器带参数跑一个工具）。客户端和服务器之间的“线路”可以是同一台机器上的标准输入输出（stdio），也可以是 HTTP、WebSocket，课程项目用的是 stdio[O2]。
        4. 对着下图，把 L2 的 12 步流转压成一句话：应用先向 MCP 服务器要工具列表，连同用户问题发给 Claude；Claude 决定用哪个工具，应用再让 MCP 客户端去执行，结果交回 Claude 写最终回答[O2]。

        做完的标准：不看课程，能在纸上画出“应用、Claude、MCP 客户端、MCP 服务器、外部服务”五个方框和两次 MCP 往返，并说出 MCP 与 tool use 的区别。

        补充说明：课程页面配有讲者视频，本手册没有转写；正文已覆盖每课的操作，想看讲者演示时再打开课程页。图里省略了最后一段“应用把 Claude 的回答显示给用户”。

        步骤 2 把课程项目跑起来，认清 6 个待补位置

        整门课都在补同一个小项目：一个命令行聊天程序，自带一个内存里的“文档库”MCP 服务器。先让它能启动，再看清每个待补位置属于后面哪一步。

        目标：项目依赖装好、.env 填好，并能说出 mcp_server.py 与 mcp_client.py 里每个待补位置对应的课次。

        1. 从课程 L3 页面的下载链接拿到 cli_project.zip，解压到一个不在其他仓库里的目录，例如〔~/code/mcp-course/cli_project〕[O3]。完整版 cli_project_COMPLETE.zip 也一起下好，单独解压，只用来对答案。
        2. 在项目目录运行 uv sync。项目自带 uv.lock，2026-10-27 实装的是 mcp 1.8.0 和 anthropic 0.51.0；课程 README 写的是 uv venv + uv pip install -e .，那种装法不读 uv.lock，只按 pyproject.toml 的范围取版本；用 uv sync 才能保证装的是 1.8.0。两种都不要升级到 2.x（见 G2）[O11、O14]。
        3. 打开 .env：CLAUDE_MODEL 已预设为 claude-haiku-4-5，USE_UV=1 表示用 uv 启动服务器；把自己的 key 填进 ANTHROPIC_API_KEY。.env 已在项目的 .gitignore 里，不要把它复制进别的仓库[O11]。
        4. 打开 mcp_server.py，6 个待补位置依次是：读文档工具、编辑文档工具、返回全部文档 ID 的资源、返回单篇内容的资源、改写成 Markdown 的提示、总结文档的提示。文档就存在同一文件的 docs 字典里，键是文档 ID（如 report.pdf），值是一句话内容[O11]。
        5. 打开 mcp_client.py，5 个方法（list_tools、call_tool、list_prompts、get_prompt、read_resource）都只返回空值；文件底部的 main()（mcp_client.py:79-85）是留给你自测的入口，里面只有 pass，默认用 uv run mcp_server.py 启动服务器[O11]。

        做完的标准：uv sync 无报错；.env 三个变量都有值；你在待补位置旁边标出了步骤号（3、3、6、6、7、7）。

        项目自带的约定：聊天里输入 @文档ID 会把文档内容带进问题，输入 / 会列出服务器提供的命令；uv run main.py 〔另一个服务器.py〕 还能再挂上别的 MCP 服务器[O11]。这些功能要等步骤 5–7 补完客户端才会生效；@ 和 / 的处理在 core/cli_chat.py:21-63，补全列表在 core/cli.py:179-197。

        参见附录：不做 / 依据 / 改为。

        步骤 3 用装饰器写两个工具

        这一章开始写服务器。SDK 的装饰器会根据函数签名自动生成 JSON schema（描述参数名、类型、说明的一段 JSON，Claude 靠它知道该怎么传参），你只写 Python 函数和描述。

        目标：在 mcp_server.py 里写出 read_doc_contents 和 edit_document 两个工具。

        1. 确认文件顶部已有 mcp = FastMCP("DocumentMCP", log_level="ERROR")，并补一行 from pydantic import Field。Field 是数据校验库 pydantic 提供的参数说明写法，这里用来给每个参数写描述[O3]。
        2. 写读文档工具：用 @mcp.tool(name="read_doc_contents", description=...) 装饰一个函数，参数 doc_id: str = Field(description=...)；ID 不在 docs 里就抛 ValueError，否则返回内容[O3、O12]。
        3. 写编辑工具 edit_document：三个参数 doc_id、old_str、new_str，做一次查找替换后写回 docs；old_str 的描述里写明“必须逐字匹配，包括空白”，这句话是写给 Claude 看的[O3、O12]。
        4. 描述写成完整的一句话，说清工具做什么、参数是什么。Claude 只能靠名字和描述决定什么时候调用它[O3]。
        5. 先不跑聊天，直接进步骤 4 用 Inspector 测；Inspector 不需要 API key[O4、O14]。

        做完的标准：mcp_server.py 里有两个带描述的工具，每个参数都用 Field 写了描述，不存在的 ID 会抛错而不是返回空字符串。

        实测：用完整版的服务器在 SDK 1.8.0 上调用，read_doc_contents 读 report.pdf 返回原句；edit_document 把 20m 换成 25m 后返回内容为空、isError 为 false；读不存在的 nope.md 时 isError 为 true，错误文本里带着你抛出的那句话[O14]。

        参见附录：案例 3。

        步骤 4 用 Inspector 测工具，不接聊天程序

        Inspector 是 SDK 自带的浏览器调试页面，能单独连上你的服务器，列出工具、填参数、看返回。以后每加一个功能，都先在这里测通再接客户端。

        目标：在 Inspector 里完成三次测试：正常读、先改后读、读一个不存在的 ID。

        1. 在项目目录运行 uv run mcp dev mcp_server.py。终端会打印一个 http://127.0.0.1:6274?... 开头的地址并自动打开浏览器；第一次运行要等 npx 下载 Inspector（见 G3）[O4、O14]。
        2. 点 Connect，状态从 Disconnected 变成 Connected 后，进 Tools 页点 List Tools，应看到你写的两个工具和参数说明[O4]。
        3. 选 read_doc_contents，doc_id 填 deposition.md，点 Run Tool，核对返回的是字典里那句话[O4]。
        4. 选 edit_document 改 report.pdf 里的一个词，再用读工具读一次，确认改动还在。Inspector 在多次调用之间保留服务器状态，所以能这样串着测[O4]。
        5. 用读工具读一个不存在的 ID，确认界面显示的是错误而不是空结果；在 1.8.0 上错误文本里能看到你抛出的那句话[O14]。测完在终端按 Ctrl+C 停掉。以后改了 mcp_server.py，都要停掉重开 mcp dev 才能看到新代码。

        做完的标准：三次测试的结果都和预期一致，且你能说出“先改后读”为什么在 Inspector 里成立。

        说明：课程提醒 Inspector 界面在持续改版，按钮位置可能和课程视频不同，但连接、列出、运行这三个动作不变[O4]。本手册只核过 2.12.0 能启动并给出地址，界面按钮未逐个核对[O14]。

        步骤 5 写客户端，让 Claude 调到你的工具

        服务器测通后，补客户端这一侧。课程说明：真实项目里一般只写客户端或只写服务器，这门课两边都写，是为了看清它们怎么配合[O5]。

        目标：补全 list_tools 和 call_tool，先用脚本自测，再在聊天里让 Claude 读出 report.pdf。

        1. 看懂 MCPClient 的结构：connect() 用 StdioServerParameters 启动服务器进程，再建一个 SDK 的 ClientSession；AsyncExitStack 负责退出时关掉连接和子进程。这个封装就是为了不漏清理[O5、O11]。
        2. list_tools：调用 self.session().list_tools()，返回结果里的 tools 列表[O5、O12]。
        3. call_tool：把工具名和 Claude 给的参数原样交给 self.session().call_tool(...)，返回结果对象[O5、O12]。
        4. 在文件底部 main() 的 async with 里调用一次 list_tools() 并打印，运行 uv run mcp_client.py，应看到两个工具的名字、描述和输入 schema[O5]。
        5. 有 key 时运行 uv run main.py，问“report.pdf 里写了什么”。幕后顺序是：应用取工具列表 → 连同问题发给 Claude → Claude 选 read_doc_contents → 应用通过客户端执行 → 结果交回 Claude 作答[O5]。

        做完的标准：uv run mcp_client.py 打印出两个工具；有 key 时，Claude 的回答里出现 report.pdf 的那句话。

        补充说明：core/tools.py 已经写好了“把 MCP 工具转成 Claude 能用的格式、执行后把结果交回”的逻辑，你只补客户端的两个方法；想看清 Claude 那一侧怎么接，读这个文件即可[O11]。

        步骤 6 加资源，做 @ 提及

        工具是让 Claude 去做事；资源是让你的应用自己取数据。课程的场景是 @文档名：输入时要补全文档列表，选中后直接把内容放进问题，省掉一次工具调用[O6]。

        目标：服务器有两个资源（文档列表、单篇文档），客户端能按 MIME 类型（说明数据格式的标签，如 application/json）读出来，聊天里 @ 提及可用。

        1. 写直接资源：@mcp.resource("docs://documents", mime_type="application/json")，返回全部文档 ID 的列表。直接资源的 URI 固定、不带参数；返回 Python 列表即可，SDK 会自动序列化[O6、O12]。
        2. 写模板资源：URI 写成 docs://documents/{doc_id}，mime_type="text/plain"，函数参数名和花括号里的名字一致，SDK 解析 URI 后按关键字参数传入[O6、O12]。
        3. 用 uv run mcp dev mcp_server.py 测：直接资源在 Resources 栏，模板资源在 Resource Templates 栏[O6]。
        4. 补客户端 read_resource：用 AnyUrl(uri) 发请求，取 contents 的第一个元素；MIME 是 application/json 就 json.loads 后返回，否则返回文本。需要的 import 是 json 和 from pydantic import AnyUrl[O7、O12]。没有 key 时，在 main() 里分别读 docs://documents 和 docs://documents/report.pdf 并打印：前者应是 Python 列表，后者应是字符串[O14]。
        5. 重启 uv run main.py（补全列表只在启动时取一次），输入 @，应弹出文档补全；选一篇提问，Claude 不需要再调读文档工具就能回答[O7]。@文档ID 前后要留空格，例如 @report.pdf 里写了什么：程序按空格切词、要求和文档 ID 完全相等，连着汉字或中文标点就匹配不上，内容不会注入，Claude 会改用读文档工具（core/cli_chat.py:35-49）[O11]。

        做完的标准：Inspector 两栏各看到一个资源；main() 自测打印出列表和正文；有 key 时，聊天里 @ 补全列出 6 篇文档。

        实测：在 SDK 1.8.0 上，模板资源的列表项里 mimeType 显示为空，实际读取时返回 text/plain[O14]。在 1.8.0 的 Inspector 里看到模板资源没标类型，不是你写错了；2.3.0 的表现见附录 E2。

        步骤 7 加提示，做 / 命令，自己补上 summarize

        提示是服务器作者预先写好、测过的指令模板。用户自己也能让 Claude“把这篇改成 Markdown”，但作者写的专用提示能把边界情况处理好、结果更稳定[O8]。

        目标：服务器有 format 和 summarize 两个提示，客户端能列出和取用，聊天里 /format、/summarize 可用。

        1. 写 format 提示：@mcp.prompt(name="format", description=...)，参数 doc_id，返回消息列表（from mcp.server.fastmcp.prompts import base，用 base.UserMessage(...)）。指令内容自己写：要求把指定文档改写成 Markdown、用 edit_document 写回、不解释改动[O8、O12]。
        2. 写 summarize 提示：起步项目的最后一个待补位置就是它，README 的用法示例也是 /summarize deposition.md，但完整版里没有实现（见案例 1）[O11、O12]。照 format 的结构写，指令改成“读文档并总结”；参数必须叫 doc_id，因为客户端写死了这个参数名（core/cli_chat.py:33、:58-60）[O11]。要求清单见模板 T2。
        3. 用 Inspector 的 Prompts 页测两个提示：填 doc_id 后看实际生成的消息，确认文档 ID 已插进去[O8]。
        4. 补客户端：list_prompts 返回 prompts 列表；get_prompt(prompt_name, args) 把参数字典原样传过去，返回结果里的 messages。参数字典里的键会变成提示函数的关键字参数，例如 {"doc_id": "plan.md"}[O9、O12]。没有 key 时，在 main() 里打印 list_prompts() 和 get_prompt("format", {"doc_id": "plan.md"})：应看到 1 条 user 消息，内容里有 plan.md[O14]。
        5. 重启 uv run main.py，输入 /，按 Tab 补全选 format，再选文档；预期 Claude 会读出内容后用 edit_document 写回（本手册未跑聊天，not_tested）[O9、O11]。/命令 后面必须带一个文档 ID：只输 /format 就回车会抛 IndexError，程序直接退出，因为主循环只捕获 Ctrl+C（core/cli.py:199-210）[O11]。

        做完的标准：Inspector 的 Prompts 页能看到两个提示；main() 自测打印出 1 条含文档 ID 的消息；有 key 时，/summarize 〔某篇文档〕 返回一段总结，且没有改动文档。

        实测：完整版的 format 提示在 1.8.0 上返回 1 条 user 消息，且消息里包含传入的文档 ID[O14]。

        步骤 8 按“谁控制”给三种原语分工，对照完整版收尾

        目标：填完一张分工表，说清课程项目里每个功能为什么是工具、资源或提示；再拿自己的一个功能做一次同样的判断。

        1. 记住三条：工具由模型控制，Claude 决定何时调用；资源由应用控制，应用决定何时取、怎么用（补全列表、注入上下文）；提示由用户控制，用户通过斜杠命令或按钮触发[O10]。
        2. 对照下图，把课程项目的 6 个功能填进模板 T1 的分工表，每行写清“谁触发”[O10、O12]。
        3. 从你自己的项目里挑一个功能，按同样三问判断：要给 Claude 新能力 → 工具；应用要取数据放进界面或上下文 → 资源；要给用户一个预设工作流 → 提示[O10]。用 video-mcp 举例的话，见附录 E。
        4. 只对比两个改过的文件：diff mcp_server.py 〔完整版目录〕/mcp_server.py，mcp_client.py 同理（起步项目和完整版只差这两个文件）[O12]。预期会看到这些差异，都不算错：完整版留着全部待补注释和一段注释掉的旧方法（mcp_client.py:47-68），import 写在文件中间，call_tool 的参数少了 : dict 类型标注（mcp_client.py:73-74），函数名不同（如读工具的函数叫 read_document，资源函数叫 list_docs、fetch_doc），描述与提示措辞不同，以及完整版没有 summarize。
        5. 回到步骤 1 的那张流程图，在旁边补上资源和提示各走哪条路：资源由应用在 Claude 之前取，提示由用户命令触发后再交给 Claude[O7、O9]。

        做完的标准：分工表 7 行都有“谁触发”，且你自己的那个功能写了判断理由。

        补充说明：课程用 Claude 自己的界面举例：提示对应用户一键触发的工作流按钮，资源对应“从 Google Drive 添加”这类由应用取数据的功能，工具则是 Claude 执行代码、做计算时在幕后调用的[O10]。

        附录 D｜术语表
        术语 白话解释
        MCP（Model Context Protocol） 让 AI 应用和外部工具、数据之间用统一格式对话的协议
        MCP 服务器 把某个外部服务包装成一组标准工具、资源、提示的程序；课程里是 mcp_server.py
        MCP 客户端 你的应用里负责连服务器、收发消息的那部分；课程里是 mcp_client.py 的 MCPClient
        tool use（工具使用） Claude 在回答中决定调用某个工具、给出参数的机制；MCP 负责把工具提供出来
        原语 MCP 服务器能提供的三类东西：工具、资源、提示
        stdio 标准输入输出；客户端把服务器当子进程启动，用管道收发消息
        JSON schema 描述参数结构的 JSON；SDK 根据函数签名自动生成
        URI 模板 带 {参数} 的资源地址，如 docs://documents/{doc_id}
        MIME 类型 告诉对方数据是什么格式，如 application/json、text/plain
        Inspector SDK 自带的浏览器调试页，用 mcp dev 启动
        FastMCP / MCPServer SDK 里写服务器用的高层类；v1 叫 FastMCP，v2 改名 MCPServer
