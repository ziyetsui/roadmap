        4. 各取 1 条试跑转写和 OCR：视频跑 node ~/.claude/skills/video-asr/scripts/asr.mjs <视频> --out <目录> --lang zh（首次需按该技能说明装模型）；图文跑 tesseract <图片> stdout -l chi_sim。只记“能不能跑、大概多久、错字多不多”，不调参数 [O9]。
        5. 每次调用写一行 calls.jsonl：端点、参数摘要、HTTP 状态、业务是否有数据、是否计费、耗时。PGY 端点即使查无结果也扣费，调用前先核余额，失败不自动重试（survey-viral-search-media-asr.md:33）[O3]。

        做完的标准：

        • fixtures/ 里每个平台有视频和图文的原始响应；有一份字段记录，写明直链有效期、字幕字段、图文图片与正文字段是否存在。
        • 视频转写和图文 OCR 各试过 1 条，结果（成功、失败及原因）写进记录；没跑通就写没跑通。

        补充说明：

        • 0002 §2 说“原视频能拿到”“画廊由后端带 Referer 下载后引用本地文件”，这一步验证的就是这些结论在今天是否仍成立 [O2]。
        • 为什么先抓样本再写代码：课程把“当前知道什么、还缺什么”列为计划的上下文（Context）部分，缺了就会“凭空 Plan”（L05「G4C」，course.md:1648-1670）[O1]。

        参见模板：T1 运行目录与记录文件。

        步骤 2 先写工具契约、停止条件、预算和日志格式

        这一步不产出业务结果，但决定后面每个工具出错时会不会“看起来成功”。课程的说法是：工具（课程叫 Action，指一个业务上完整的操作）的能力边界、参数和返回要写清楚，执行前用代码检查，不交给模型猜（L09，course.md:3494、3620-3660）[O1]。M0 的流程是固定的（召回 → 文本稿 → 拆解 → 复刻），调研结论是不需要做通用的 Agent 循环，由编排代码按顺序调各个工具即可（study-agent-harness-patterns.md:81）[O5]。

        目标：写出 5 个工具的契约文件和一份共用的停止、预算、日志规则，后续每个步骤实现工具时照着填。

        1. 按 0002 §5 的工具名写契约：search_viral、fetch_media、transcribe、dissect、replicate_plan。每个写名称、能做什么、适用与不适用场景、必填参数、返回字段（L09「Action 如何描述」，course.md:3620-3640）[O1、O2]。两类内容用同一组工具，参数里带 content_type: video | image_note；transcribe 对视频做语音转写，对图文做“正文 + OCR”，这是助手建议，工具名要不要改由你定。
        2. 每个工具的返回分两层：调用状态（成功、参数错、没权限、超时、上游失败、查无结果）和业务是否合格（例如视频能否播放、图文图片是否齐）。参照 w5：参数不合法时返回带 code、message 的结构化错误，而不是抛异常（w5 server.py:327-353）[O6]；工具出错要返回给编排代码可读的错误，并标明能不能重试（study-agent-harness-patterns.md:36-38）[O5]。
        3. 写停止条件。课程把每一轮之后的去向归成六种：继续、完成、澄清、重试、重新规划、报错中断（L08「TAO 有哪些下一步」，course.md:3348-3362）[O1]。落到 M0：偶发网络错误才重试，且有次数上限；PGY 端点不重试；缺输入就停下来问你；同一条连续失败就跳过并记录，不让整批卡住。
        4. 写预算 budget 段：每次运行的最大调用次数、最大花费、每条素材的超时。课程建议预算包含剩余时间、最大轮次、最大查询数等，并在预算不足时主动降级（L21「基于预算的动态检索」，course.md:7323-7351）[O1]。具体数值等 G2 的余额确定后再填，先填“未定”也比没有这一段好。
        5. 定日志格式：每个步骤往 events.jsonl 写一行，至少含运行 ID、步骤、内容 ID、内容类型、输入文件、输出文件、状态、耗时、错误。课程要求 trace（把一次执行经过的每个决策点记下来）能回答“当时理解成了什么、用了什么参数、工具返回了什么”（L24「Agent 可观测性的基础做法」，course.md:7927-7955）[O1]。

        做完的标准：

        • 5 个工具都有契约，能回答“缺什么参数会被拒、返回什么才算可以继续、什么情况不重试”。
        • 停止规则、预算段、日志字段写进同一个设计文件，后续步骤直接引用。

        补充说明：

        • 0002 §5 要求最后把这 5 个工具做成 MCP 工具并通过 make check，但没有排时间，见阻断缺口末段。若三天内要做，参照 w5 的写法：服务启动时初始化资源（lifespan，w5 server.py:42-249），工具函数只做参数检查和结构化返回，业务逻辑放到单独的协调层 [O6]。
        • 不要把 w5 的“受控重试”误当成通用恢复机制：它只在 SQL 校验失败时把错误回送给模型重写，最多 max_retries + 1 次（w5 orchestrator.py:373-422）[O6]。

        参见模板：T2 工具契约、T3 日志一行；不采用的做法见附录 B。

        步骤 3 把 brief 规范化成可检查的需求

        广告主的 brief 往往是口语：“要高级感”“做出爆款”“别太硬广”。课程第 1 讲的判断是，任何没有量化的形容词都会让结果漂移，要把它变成调用工具时的参数或判定标准（L01「可量化是一件极为重要的事情」，course.md:446-470）[O1]。这一步把 brief 里的硬约束（不能违反的，如禁用表达）和软偏好分开，后面每一步都对照它。

        目标：得到一份结构化 brief.md，每个字段能回到 brief 原文，硬约束单独列出。

        1. 保留原文，再抽字段：品牌、产品、卖点、目标人群、使用场景、目标平台、内容类型（视频、图文或两者）、禁用表达、交付格式（0002 §6 brief.md 的定义）[O2]。每个字段后面注明来自原文哪一句；原文没有的写“未提供”，不由模型补。
        2. 给负责规范化的提示词划清边界：只做指代消解、补全省略、统一术语、判断要不要问你；不做最终推荐、不补产品事实、不猜低把握的内容（L01「Prompt 撰写要点」职责表，course.md:307-330）[O1]。
        3. 把形容词改写成可检查的标准，例如“高级感”拆成画面、配色、语气的具体要求，“爆款”拆成平台、时间窗、互动指标的筛选口径；拆不出来的列为待问问题（L01，course.md:446-470）[O1]。
        4. 硬约束单独成表，后面每次调用模型都原样带上，不允许摘要或改写。课程提醒，重新规划时如果不再次强调约束，会出现偶发的违背硬约束（L06「再次强调约束」，course.md:2338-2344）[O1]。

        做完的标准：

        • brief.md 里每个字段都能指回原文；“未提供”和“待问”单独列出。
        • 硬约束（尤其禁用表达、不能宣称的功效）逐条可见，没有被改成“尽量”。

        补充说明：

        • “G4C”是课程给计划定的五个要素：目标（Goal）、上下文（Context）、选择（Choice）、检查点（Checkpoint）、纠偏（Correction）（L05，course.md:1648-1670）[O1]。M0 的流程已由 0002 定死，这一步只用到前两个：目标就是 0002 的验收标准，上下文就是 brief.md 里“已知、未知、硬约束”三栏。
        • 待问问题在 11:00 前集中发给你，不要边跑边猜。

        参见模板：T4 结构化 brief、P1 规范化提示词。

        步骤 4 扩词，并多路召回视频和图文

        直接拿 brief 原句去平台搜索，结果通常很散。课程的做法是先问“为了完成目标还缺什么信息”，再决定查什么、去哪查（L18，course.md:5973-6003）[O1]。M0 的查询空间就是两个平台的搜索、热词和热榜接口，0002 已定好扩词和多路搜索的组合（0002 §2）[O2]。

        目标：得到一份带热度的词表 keywords.json，以及合计至少 200 条、带内容类型标记的候选 candidates.jsonl。

        1. 用 LLM 从 brief 的产品、卖点、人群、场景展开 10–20 个场景词，再调 pgy/get_keyword_related 换成用户真实搜索词，用 pgy/get_keyword_stat 比较热度后筛词（survey-viral-search-media-asr.md:28-29、37-40）[O3]。课程的 5W1H（谁、什么、何时、何地、为何、如何）可以用来检查词表有没有漏掉某个维度（L18，course.md:6263-6290）[O1]。
        2. 多路召回：小红书 search_notes、抖音 fetch_video_search_v2，加小红书内容广场 get_content_square 和抖音热榜（survey-viral-search-media-asr.md:23-31）[O3]。两类内容在同一批路由里召回，每条打上 content_type；小红书搜索的笔记类型筛选在调研里只记了“视频笔记”这个取值，图文的取值执行时按接口文档核对 [O3]。
        3. 所有来源写成统一结构：平台、原生 ID、内容类型、标题、正文、互动数、发布时间、抓取时间、召回路由、原始 JSON 位置。课程建议多路召回的结果统一结构，否则无法过滤、去重和排查（L20「多路、多源召回」，course.md:6789-6803）[O1]。
        4. 搜索结果不带互动数，要逐条拉详情补上（study-vita-api-fetch-recall-asr.md:18；0002 D1 写“补上 liked_count”）[O4、O2]。拉不到的字段写 null，不写 0。
        5. 每次调用记 calls.jsonl。PGY 返回 200 即扣费，查无结果不自动重试；蒲公英（PGY）是达人商业合作数据，不是聚光广告报表，不要把它的数字当投放效果（survey-tikhub-xhs-juguang-douyin-index.md:8）[O3、O8]。

        做完的标准：

        • keywords.json 每个词有来源（LLM 展开或平台关联词）和热度字段。
        • candidates.jsonl 合计 ≥200 条（0002 目标），视频与图文分别计数；不足时写实际数和原因（哪一路少）。

        补充说明：

        • 召回数量不足 200 时，先看是词的问题还是路由的问题，再决定补词还是加路由；不要靠重复调用凑数。
        • 两类候选的比例 0002 没有规定（G6），D1 中午前请你给一个大致配额，否则排序阶段可能图文太少。

        参见模板：T5 候选一行。

        步骤 5 去重、过滤，分别排出视频和图文的 Top N

        召回很多不等于可用。课程把这一段拆成四件事：过滤、合并去重、混合排序、业务规则调整，并强调“硬约束决定能不能留下，排序只决定谁排前面”（L20，course.md:6805-6865）[O1]。视频和图文的互动规模不同，放在一起排会互相挤占，所以各排各的。

        目标：得到 ranked.json，视频 Top 20、图文 Top N（N 待定），每条有分数分项和入选理由，并对照 few-shot 写出 D1 小结。

        1. 去重：以“平台 + 原生 ID”合并，多路召回到的同一条保留全部路由（L20「结果合并与去重」，course.md:6813-6821）[O1]。
        2. 过滤：命中 brief 硬约束的（如禁用品类、时间窗外）直接删除并记理由，不靠把分数调成 0 来压低（L20「过滤」，course.md:6805-6811）[O1]。
        3. 打分：按 0002 §2，brief 与候选算向量相似度，再乘热度加权；M0 在内存里计算，不建向量库（0002 §2；survey-viral-search-media-asr.md:44-50）[O2、O3]。热度可参考 xhsgrowth 的“潜力值 = 点赞 / 粉丝”（study-vita-api-fetch-recall-asr.md:48）[O4]。此时还没有转写，相似度只能用标题、正文、标签，转写拿到后可二次排序。
        4. 视频、图文分别排序取 Top N，ranked.json 每条写各项分数、配置版本、缺失字段和入选理由。课程提醒自定义加权最难在不同分数的尺度不统一，所以要把每一项单独记下，方便事后调权重（L20「混合排序」，course.md:6823-6847）[O1]。
        5. 18:30 对照 few-shot：两类分别数 Top N 里命中几条你的历史选择，写 D1 小结（0002 D1 18:30–19:00）[O2]。课程建议看长尾失败，不只看平均（L20「如何衡量检索效果」，course.md:6867-6889）[O1]，所以把没命中的几条单独列出原因。

        做完的标准：

        • ranked.json 有视频 Top 20 和图文 Top N 两组，每条可解释为什么入选。
        • D1 小结写了两类各自的 few-shot 命中数；没有 few-shot 就写“无对照基准”。

        补充说明：

        • 命中率偏低时，0002 §7 的应对是 D2 上午先调扩词和打分权重，拆解顺延半天 [O2]。这相当于课程说的 Replan（重新规划：原路径不合适时换一条路走）；改之前把旧的 ranked.json 留一份，方便对比。
        • RRF（倒数排名融合：只看每一路里的排名、不看原始分数的合并方法）适合多路分数不可比时用（course.md:6823-6829）[O1]，是否换用由你看 D1 结果再定。

        参见模板：T6 排序一行。

        步骤 6 取回素材，转成文本稿

        拆解只能吃文本和图片，所以每条入选内容都要变成“本地素材 + 文本稿”。视频的文本稿是逐字稿；图文的文本稿是正文加图中文字（OCR）。课程提醒，OCR 只识别出文字，没有解读图片，流程图、对比图之类需要再用能看图的模型补描述（L19「图片的处理方式」，course.md:6475-6481）[O1]。

        目标：Top N 每条都有本地素材和文本稿，视频能在本地播放，图文图片齐全，并留下每条的耗时记录。

        1. 拿到链接立刻下载，存到 media/。小红书 CDN 会校验 Referer（请求头里说明“从哪个页面来”的字段），浏览器直接请求会被拒绝，下载时要带 Referer: https://www.xiaohongshu.com/；抖音直链带过期签名（survey-viral-search-media-asr.md:7）[O3]。下载失败就重新拉详情换新链接（0002 §7；study-vita-api-fetch-recall-asr.md:19）[O2、O4]。
        2. 视频：小红书笔记带字幕字段的优先用字幕，取不到或是占位稿再走 ASR（自动语音识别）（study-vita-api-fetch-recall-asr.md:28；0002 §2）[O4、O2]。ASR 用本机 SenseVoice，输出 txt、srt、json 三种（0002 §6 transcripts/<id>.{txt,srt,json}）[O2]。用 ffprobe 核时长和音轨，没有音轨的标出来，不生成空逐字稿。
        3. 图文：下载全部图片，按原顺序编号保存（助手建议 media/<platform>-<id>-01.jpg 起）；正文原样保存；每张图跑 OCR，结果按图序写进 transcripts/<id>.json，transcripts/<id>.txt 是“正文 + 各图文字”的合并稿。图上主要是画面、几乎没字的，ocr_text 为空并标 image_only，留给步骤 7 用看图模型描述。课程的第三种做法正是“同时保存原图和文本描述”，文本用于检索和拆解，原图留作证据（L19，course.md:6485）；小红书图文的图片地址字段见 study-vita-api-fetch-recall-asr.md:39 [O1、O4]。
        4. 给每个文件标可信状态：课程建议中间结果至少分“已验证、可暂用、无效”几档（L07「给中间结果标记可信状态」，course.md:2612-2640）[O1]。视频以“能播放、逐字稿非空”为已验证；图文以“图片张数与详情一致、正文非空”为已验证；OCR 结果默认只算可暂用。
        5. 每条写一行 timings.csv：拉详情、下载、转写或 OCR、校验、合计，失败的也记。调研估计一条 60 秒视频端到端约 5–20 秒、瓶颈在下载（survey-viral-search-media-asr.md:12-16），这是估计值，以你的实测为准 [O3]。

        做完的标准：

        • 视频：Top 20 本地可播放、逐字稿齐全；60 秒视频端到端中位数 ≤20 秒是 0002 目标，按实测样本算，不足 20 条或没有 60 秒样本时写实际情况 [O2]。
        • 图文：Top N 每条图片齐全、正文与 OCR 合并稿已生成；“齐全”和耗时标准待你确认（G6），确认前只报实际数。
        • timings.csv 含成功和失败两部分，失败条有原因。

        补充说明：

        • 只有字幕或 ASR 本身带时间戳时才生成 srt，不按时长平均切时间伪造字幕。
        • 同一条内容重跑时先查本地是否已有已验证的文件，有就跳过，不重复下载、不重复付费。这就是“幂等”：同一操作做两次和做一次结果相同。

        参见模板：T7 文本稿。

        步骤 7 用同一个框架拆解视频和图文，搭画廊，人工抽查

        拆解要回答“这条为什么火、哪些可以复刻”。0002 已定拆解维度：单篇拆钩子、结构、人群、价值点、画面，Top 5 再总结标题公式、内容模板、视觉风格和复刻指南（0002 §2，来源 xhsgrowth ai.ts:53-122）[O2、O4]。两类内容用同一套维度，图文多一项“图序与封面”。课程强调，模型拿到工具结果后，解释数据比存储数据更重要（L08「Observation」，course.md:3318）[O1]——所以拆解结论要指回原文或原图，而不是只写印象。

        目标：Top N 每条有一份结构化拆解，两类各有一份 Top 5 共性总结，画廊能离线查看全部结果，你抽查后提示词已修订。

        1. 单篇拆解：视频输入逐字稿、1fps 切镜关键帧和文案（关键帧做法见 study-vita-api-fetch-recall-asr.md:32）；图文输入正文、OCR 文本和按图序排好的图片 [O2、O4]。输出同一组字段：钩子、结构、目标人群、卖点、表达与画面；图文多 image_sequence（每张图的作用）和 cover（封面写了什么、为什么抓人）。每个结论带依据：视频写时间点，图文写第几张图或正文哪一句。
        2. 输出先过结构检查：字段缺失、依据为空、引用了不存在的图序号，就带着错误信息让模型重写一次，再失败就标“拆解失败”。这参照 w5 把校验错误回送给模型重写的做法（w5 orchestrator.py:373-422）[O6]；课程把这类“怎么知道这一步做对了”的检查叫检查点（Checkpoint）（L05，course.md:1851-1867）[O1]。
        3. Top 5 共性：两类分开写进 dissect/summary.md 的两节。视频总结标题公式、开头 3 秒钩子、内容结构、视觉风格、复刻指南（0002 D2）；图文总结标题公式、封面与首图、图序结构、正文结构、复刻指南 [O2]。拆解提示词用 Top 5 做 few-shot 例子，不写长篇规则（study-agent-harness-patterns.md:86）[O5]。
        4. 画廊 gallery/index.html：视频网格加图文卡片，点开看逐字稿或正文与 OCR、拆解结果；媒体全部引用本地文件（0002 D2 15:00–17:30）[O2]。
        5. 17:30 人工抽查：你按“拆得对 / 不对 / 理由”逐条标注，按意见改提示词并留下修改前后版本（0002 D2 17:30–19:00）[O2]。课程认为专业业务最可靠的是懂行的人评审，常见做法是抽样审核（L23「专家评审」，course.md:7627-7635）[O1]。

        做完的标准：

        • dissect/<id>.json 覆盖视频 Top 20 和图文 Top N，每条结论有依据；失败条单列。
        • 画廊离线打开，逐条可播放或翻图，不出现 403 和直链失效（0002 D2 验收）[O2]。
        • 抽查记录在案：0002 目标是 5 条至少 4 条“拆得对”；两类是否各抽 5 条待你确认（G6）。

        补充说明：

        • “拆得对”要事先写成你能判断的几条标准（例如钩子是否就是开头那句、卖点是否在原文出现），否则抽查结论会随心情变化——这正是 L01 说的“可量化”（course.md:446）[O1]。
        • 画面层面的因子（镜头、节奏、字幕样式）调研建议只对头部样本用能直接看视频的模型（survey-viral-search-media-asr.md:59）[O3]，不必每条都做。

        参见模板：T8 拆解结果、P2 拆解提示词。

        步骤 8 按产品出复刻方案和成品包

        复刻不是照抄。参考内容提供结构，产品事实只能来自 brief；任何参考里有、而你的产品没有的卖点都不能写进去。课程反复强调硬约束要在后续每一步重新带上（L06，course.md:2338-2344）[O1]，这里是最容易违反它的地方。

        目标：得到 replicate/plan.md（视频方案和图文方案），以及按 0002 选定路线做出的 1 条视频成品；图文成品按你确认的范围交付。

        1. 输入固定为三样：brief.md（产品事实与硬约束）、dissect/summary.md（结构）、你挑的 1–3 条参考。输出视频方案：分镜加口播脚本、标题、封面文案、笔记正文、tag；图文方案：标题、封面文案、图序（每张图放什么、配什么字）、正文、tag（0002 D3 10:00–12:00）[O2]。
        2. 用另一个模型审核方案：逐条检查有没有违反禁用表达、有没有 brief 里不存在的功效或数字，最多驳回 2 次，仍不过就交给你人工改（study-agent-harness-patterns.md:64-66、88）[O5]。
        3. 视频成品按 G4 选定的路线：有素材用 video-use 剪辑、配字幕、配音；没有素材走 creative-workflow 的数字人流程（Kling 或 HeyGen）；数字人授权或 Key 没到位就改走有素材路线（0002 D3 13:00–16:30、§7）[O2]。
        4. 整理成品包：视频、封面、笔记、文案、tag，按小红书和抖音各出一份，放 replicate/<platform>/（0002 D3 16:30–18:00）[O2]。图文成品若确认在范围内，同样分平台存放；不在范围内就只交方案。

        做完的标准：

        • plan.md 两类方案齐全，审核记录写明驳回原因和最终处理人。
        • 有 1 条可直接发布的视频成品（0002 D3 目标）；图文按 G6 的确认结果交付，确认前只算方案。

        补充说明：

        • 时间不够时，先砍双平台成品包（只留一个平台），不砍方案和审核（0002 §7）[O2]。
        • 复刻生成可参考 vita-api 里已有的写作技能目录（study-vita-api-fetch-recall-asr.md:53），它们是私有仓库内容，只作写法参考 [O4]。

        参见模板：P3 复刻审核提示词。

        步骤 9 人工验收，写 run-report

        M0 的价值是留下一份生产基线：每一步多久、花多少钱、失败多少、哪里靠人。课程说用户真正感受到的是端到端多久拿到靠谱结果，而且不要只看平均数，要看 P50、P95（一半和 95% 的请求在多长时间内完成）（L21，course.md:7151-7185）[O1]。出了错，先找“首错”——最早出错的那一步，而不是报错暴露出来的那一步（L07，course.md:2534-2550）[O1]。

        目标：逐项对照 0002 验收标准给出通过、失败或未测，写出两轨分开统计的 run-report.md，并把发现的问题定位到具体步骤。

        1. 逐条核验收：D1（视频可播放、逐字稿齐全、耗时中位数）、D2（画廊无 403、抽查 4/5）、D3（1 条可发布成品、目录可复现、报告完整）；图文项按 G6 的确认结果核，未确认的写“未定标准”，不写通过 [O2]。
        2. 从 timings.csv 和 calls.jsonl 算两轨各自的耗时 P50 / P95、调用次数、花费、失败率，失败条不删。课程提醒性能要和准确率一起看，不能为了快牺牲召回（L21「性能不能脱离准确率讨论」，course.md:7209-7227）[O1]。
        3. 有问题的结果按检查点倒查：从最终产物往前，找到最后一个可信的中间文件和第一个不可信的，错误就在两者之间（L24「借助 Checkpoint 快速定位」，course.md:7999-8045）[O1]。例如复刻方案出现禁用词，就依次查 brief.md 有没有、拆解有没有带进来、方案提示词有没有带上硬约束。
        4. 写 run-report.md：每个环节的耗时、成本、成功率、哪些环节靠人工、M1 待办（0002 §5 第 4 项）；每个数字注明样本数和统计口径 [O2]。图文验收数字若仍未定，单列为 M1 前必须确认的事项。
        5. 收尾：若你决定三天内收进 MCP 工具，在项目根目录跑 make check 并记录结果（0002 §5 第 5 项）[O2、O9]；没做就在报告里写“未收进 MCP 工具”。

        做完的标准：

        • 0002 每条验收都有“通过 / 失败 / 未测”和证据文件路径；图文项没有标准的写“未定标准”。
        • run-report.md 两轨分开统计，数字都能追到 timings.csv、calls.jsonl 或抽查记录。

        补充说明：

        • 修复后只重跑首错之后受影响的步骤，前面已验证的文件直接复用；课程把这叫“已有结果复用率”，是评估重新规划好坏的指标之一（L07，course.md:2886-2892）[O1]。
        • run-report 是 M1 的输入：0002 写明 M1 的 PRD、设计和实施计划要等 run-report 出来后再写（specs/index.md 的 Build order）。

        参见模板：T9 run-report 骨架；案例见附录 C。
